# Live Climbs V1 Architecture

Live Climbs is the hero competitive experience: a user picks a real-world landmark (Empire State Building, Burj Khalifa, etc.), races against past attempts in real time via headphone-motion step tracking, and either reaches the target step count (completion) or doesn't (failed attempt).

For adding, editing, releasing, or validating catalog content and images, use the `live-climb-content` skill.

## Surface architecture
- Live Climbs lives on a 3-screen loop: **Home** (a stateful entry card showing the day's recommended climb), **Browse** (a searchable globe for discovery), and **Climb Detail** (the primary destination - overview, your history, per-climb leaderboard).
- Home shows one concrete recommended climb per day, persisted per local calendar day so it stays consistent even if completion state changes mid-day. The card is fully tappable; no extra in-card CTA chrome.
- Browse treats the globe and bottom drawer as distinct navigation modes: globe pin taps open a compact preview card; search/list/section taps open Climb Detail directly. Search lives in the drawer and expands above the keyboard when focused. Globe state (zoom, preview, search) clears when re-entering Browse from elsewhere.
- Climb Detail uses a flippable hero card (landmark image on the front, tier + fun fact on the back) and three swipeable pages: overview, personal history, per-climb leaderboard. The leaderboard page uses the per-climb leaderboard pattern defined in the `ascend-leaderboards` skill.
- Globe pins are state-driven: hollow outline for available climbs, filled with double-pin glow for the active climb, filled check badge for completed climbs.
- Hardware-capability gating (headphones required) belongs at the *start-attempt* moment, not as warnings on Home or Browse, and the blocking gate stays inline at start-attempt. The *worded* explanation lives in the first-climb coach mark and, blocking and for everyone, in the session gate - not on the Climb Detail overview, where it used to be a persistent card above the Start button and read as a hardware manual on the one screen that exists to start a race. What Climb Detail keeps is a route, not a paragraph: an icon-only control beside Start Live Climb opening `CompatibleHeadphonesHelpSheet`, carrying an assistive-technology label and hint equivalent to the deleted card's ("Compatible headphones" / "Opens the compatible headphones list."). That route may not be lost - the requirement is real, and a climber who needs the device list has nowhere else to look from this screen. Pinned by `AscendAppTests/ClimbDetailHeadphoneAffordanceTests.swift`, which drives the real view rather than a copy of it.

## Attempt model
- `ClimbAttempt` is an `@Model`: changing what it persists is a schema migration - see `ascend-data-migration`.
- The climb attempt is the source of truth for progress and history. It replaces any older completion-only model.
- Catalog climbs are *single-session challenges*: the live attempt must reach the target step count to count as a completion. Ending early saves a failed attempt in personal history; only target-reached completions count publicly (leaderboard, First Ascent eligibility).
- Live Climb completions come only from the live headphone-motion attempt flow. Routine completions cannot progress or complete a Live Climb. (Integrity gate; the canonical statement of this rule lives in `ascend-workout-model`.)
- The live attempt creates a workout only after the live session stops with recorded steps. The workout flows through the normal workout mutation pipeline so leaderboards, Best Efforts, and remote backup stay on one path.
- Reaching the climb's step target *is* the finish, and `LiveClimbCompletionPolicy` is the only place that decides it.
  Status always reads steps, never `stopReason`.
  Never add a second finish definition: readers ask the policy, they don't re-derive.
- For a climb attempt, `stopReason` describes *how* a session ended, never whether it counted; a routine session deliberately inverts that, so read the `ascend-routines` skill before reusing the enum's rules here.
  `ClimbService.apply` upgrades it to `.targetReached` for the manual-stop case only - a climber who tapped End past the target finished - so rehydration and the replay Cloud Function agree on that path.
  Every other stop reason is deliberately left as recorded.
- An interrupted recovered draft past the target counts locally as a completion but is deliberately never published by the replay Cloud Function, because a recovered draft's step count is typed by hand.
  That asymmetry is an intentional First Ascent integrity gate, not the reinstall bug it resembles: a First Ascent is permanent and never reclaimable, so a typed number must never claim one.
  Ask `LiveClimbCompletionPolicy` before changing what normalizes; don't widen it to heal a status that already reads steps.
- **A recovered draft's duration is credited to the last checkpoint, not to now.** `applyRecoveryStepSync` deliberately credits wall clock, because the draft holds no tracked duration for the stretch after the app died and a climber who kept stepping through a short dropout would otherwise be under-counted. That credit is bounded by `ActiveHeadphoneWorkoutDraftStore.maximumCreditableTrackingGap` (one hour): past it, the session is treated as having ended when tracking stopped. The bound is an hour rather than minutes because the clamp bounds duration and never the step count the climber types off the machine, so a session clamped after the climber kept stepping presents an impossible cadence and trips the device's own 220 steps/min gate in `WorkoutRemoteSyncMapper.snapshot`, which `WorkoutSyncCoordinator` treats as terminal. An hour keeps the common crash-early-and-keep-climbing shape inside the limit; it narrows that window rather than closing it. Uncapped, a draft resolved days later claimed days of duration, and `isPhysicallyPossibleClimb` in `firestore.rules` refuses anything over five days - an honest climb, permanently unsyncable, with a bare `PERMISSION_DENIED` the client cannot explain. The gap is still recorded in full on `HeadphoneMotionTrackingIntegrity`: bounding a duration claim is not the same as falsifying the record of how long tracking was unavailable.
- Saved Live Climb attempts are immutable competitive history. Discard during the live session if the attempt shouldn't count; once saved, workout-log delete affordances do not erase the underlying attempt.

## Completed-Climb Projection (globe / Collection / `totalClimbsCompleted`)

A completed climb is **1:1 with a `Workout`** (the sole canonical record; verdict in `data/verify-workout-climb-cardinality-m2`). There is no separate canonical climb collection.

- The `onWorkoutWritten` Cloud Function (`functions/src/climbCompletions.ts`) is the single site that derives the server projection `users/{uid}/landmarkResults/{climbId}` FROM the workout. One recompute is one Firestore transaction: the workout query, the projection read, and the write-or-delete all happen inside it, reads before writes, so a retry re-derives and an older snapshot can never commit over newer canonical state. Inside that transaction it still validates-before-writes (returns success without a duplicate write when the event is already reflected in `computedThroughEvent`), so the live trigger, re-delivery, and the backfill converge on byte-identical docs. It writes only the private projection and never claims a First Ascent - that stays in the replay path (`liveReplayLeaderboard.ts`).
- `ClimbCompletionRepository` (`AscendApp/Shared/Repositories/`) is the ONLY read surface for the completed set: `read` serves the local `ClimbAttempt` cache distinct-per-`climbId`; `refresh(userId:modelContext:)` pulls `landmarkResults` into the cache losslessly (only ever adds, never shows less than earned) and runs on authenticated bootstrap (`RootView.bootstrapAuthenticatedLocalState`). This makes the count correct on an in-place UPDATE, not just a reinstall.
- The globe numerator, Collection claimed state, and `totalClimbsCompleted` all read this one distinct-climb set - never a raw `@Query ClimbAttempt` for the completed set, never a `max(local, server)`. `ClimbAttempt` (SwiftData) is the repository's device cache row, not a canonical server collection.
- `landmarkResults` rules are server-derived, read-own / `write: if false` (`firestore.rules`). The idempotent, prod-refusing backfill is `scripts/backfill-landmark-results.mjs` - dry-run by default and `_migrations` ledger-gated; it plans candidate user/climb identities (canonical workouts UNION stored projections) then re-derives each one through the same transaction, so it restores missing projections and deletes orphaned ones without overwriting a concurrent live trigger. The completion predicate is the shared vector-pinned `isRecoverableLegacyCompletion` (Swift / TS / mjs, pinned by `SharedTestVectors/legacy-recoverable-completion-vector.json`) - do not author a fourth copy.

## First Ascent (World First) prestige
- Every climb has a permanent First Ascent holder - the first user to complete it. The holder's name and completion date remain associated with the climb even after their time is beaten by faster climbers. The one exception is account deletion: the claim and its date are permanent, but the name is not, so deleting an account de-identifies the record to `Anonymous Climber` while the slot stays claimed and dated (see the account-deletion rules in `ascend-firebase-data`). This creates a permanent-prestige retention loop: every new climb drop opens a fresh First Ascent slot that can never be reclaimed once held. In leaderboard surfaces, First Ascent is honored but secondary to the active top-3 chase - the *current* glory belongs to whoever holds the top times; First Ascent is a permanent annotation, not the headline.
- The universal no-finisher copy is: "First Ascent open. The first finisher claims it forever." Use it verbatim on any surface that needs to explain an unclaimed climb.

## Live session execution
- Sensor stats (time, steps, progress, SPM) update locally every second during a live session without waiting on the network. Stale or failed backend reads must never interrupt local tracking.
- The replay leaderboard is the primary visual surface during a live attempt - elapsed time + target step count in top chrome, the user's row anchors as a horizontal accent progress indicator, with an end-attempt control at the bottom. Pre-start countdown fully obscures the live UI until recording begins.
- Live attempts cannot be paused. Once recording starts, the clock runs until the user reaches the target step count (completion) or ends the attempt (DNF). If the user stops stepping or steps off the machine, the clock keeps running - competitive integrity comes from the unbroken clock, like an ultra-marathon. We don't try to detect "is the user still climbing" via motion heuristics or location; that's complexity without product value, and any rest the user takes legitimately costs them rank.
- Heart rate is optional garnish on a live session, never a gate. Chest-strap auto-connect at session start is fire-and-forget and bounded by `HeartRateMonitorService.connectTimeout` (15s) so every attempt settles to connected or failed - it must never delay or block headphone-motion step tracking. An unexpected mid-session drop is different: it enters `.reconnecting`, which is unbounded by design and must never arm the connect timeout, because firing it would tear down the transport's pending reconnect for the rest of the climb. Keep paired, transport-connected, and actively-producing-fresh-measurements distinct - the live chip resolves through `LiveHeartRateStatus` (connecting / connected reading / reconnecting / signal lost / failed), and a paired connection with no fresh sample reads "signal lost", not a stale number. Regression coverage: `AscendAppTests/HeartRateMonitorServiceTests.swift` and `AscendAppTests/LiveHeartRateStatusTests.swift`.
- A background-execution helper runs alongside the headphone-motion session so the session survives backgrounding. The helper must not write HealthKit workouts or request new Health permissions.
- A Live Activity / Dynamic Island surface mirrors session state (compact: steps + the standing pair; expanded: name + image + duration + steps + intent-driven controls). The widget extension reads from the session view model only - never Firestore, never the replay index directly. The standing is a value and the caption naming what it counted, always travelling together (`standingValue` / `standingCaption`) - `#4` over `climbers`, or `2nd` over `your climbs` where nobody else has finished - because the compact slot is too narrow for `of 27 climbers` and a bare ordinal is the defect the pair exists to prevent. Whatever the live panel states, the Lock Screen states.
- Completed sessions transition to a post-save summary before dismissal - adaptive pace splits, vertical-gain display, a Share button into the composer where the climb's recap cards are offered as backgrounds when climb metadata is available (`ascend-share-composer`), and direct affordances to add notes and media to the climb workout. The completion summary is the moment for adding context; we don't gather notes / media via a deferred review sheet.
  Nothing may cover that summary to ask the climber for something: the app-owned "Enjoying Ascend?" sentiment question after a first Live Climb is presented by `LiveClimbSessionView` once the summary has been dismissed (`AscendAppTests/LiveClimbRatingPromptPlacementEvidenceTests.swift`), and answering `Yes` still calls `AppStore.requestReview(in:)` - Apple decides whether the system prompt appears.

## Replay leaderboard architecture
- The replay leaderboard is a context-agnostic system reusable for Live Climbs and future race surfaces (challenge climbs). Don't clone climb-specific comparison logic per surface - share the context / sampler / service abstractions.
- Replay rank compares the live user's current steps against completed eligible attempts at the same elapsed-time bucket. Failed, abandoned, and partial attempts never publish into replay indexes. Tied completed attempts rank ahead of the live user (a new attempt starts at the bottom of the completed field).
- **An attempt that has already finished does not leave the race.** `publishReplayEntries` writes one entry per bucket an attempt ran for and not one more, so reading only the current bucket erased every rival already home and promoted the live climber to first the moment the leader finished. `fetchWindow` therefore reads two halves on *both* sides of the window: the rivals still running at this bucket, and the attempts whose `splitBucketCount` has been passed, held at their `finalSteps`. A landmark climb hides the behind half - every completion is at or past the target - but an open Just Climb has no target, so a rival who stopped at 200 steps vanishes the moment the climber passes 200. Rank is `aheadCount + 1` and never consults the behind side, so the behind finishers cost a fetch and no count. Both ahead halves feed the rank count, and a failed count on either side falls back to the rows on screen rather than summing a real count with a guess. The finished reads need declared composite indexes (`finalSteps` + `splitBucketCount`, ascending for the ahead half and descending for the behind half, each also with `isBestForUser`), and their fetches swallow a failure to a `debugLog`, a bounded Crashlytics report (`reportFinishedRowFailure`, at most once per read per session, because `debugLog` is compiled out of the Release build where a missing index is likeliest) and an empty half, so a missing index costs the finishers rather than the whole board. Both halves are then merged in memory, and a tie on steps is settled by the board's own `rankingMetric` rather than by document ID: a live climb clamps every recorded step count to the target and publishes only a target-reached stop, so *every* finisher holds exactly the target and the whole finished field is one tie - ordering it on ID showed the field in an arbitrary order that was never the order the climb is ranked in. The ahead half is reversed before ranking and so is ordered worst-first; the behind half is not and so is ordered best-first; an attempt already home always leads one still running. The seeded boards never showed this - `scripts/seed-live-replay-leaderboards.mjs` pads every synthetic attempt across every bucket - so only a real published attempt reproduces it.
- **The live board resolves who is viewing it.** `parseRow` takes the signed-in uid, exactly as `parseCompletionRow` does for the static board; without it every published row came back `isCurrentUser: false` and a repeat climber's own earlier attempt was drawn as a stranger - initials instead of their photo, a demographic subtitle, and a `NavigationLink` into their own "other climber" profile. `isCurrentUser` means the row belongs to the viewer, which on a repeat climber's board is true of more than one row; `isLiveAttempt` is the single row whose steps come from the live counter, and it alone gets the anchored progress treatment, the scroll anchor, the live rank, and the losing side of a tie.
  A row of the viewer's that is not the live attempt is a **ghost** (`isViewerGhost`, live-window only - the static completion board draws every completion as a ranked row and never asks it).
  Settled by the captain on 2026-09-01: a climber's previous best "is not a leaderboard row, so it takes no rank cell, is never tappable, and is never counted in the rank or the field size."
  So a ghost is subtracted from the ahead count (`OwnClimbHistory.ghostAhead`, decided from the same row the `BEST` marker draws), skipped by the projection's crossings, drawn with an empty rank cell, and left out of the `NavigationLink` and the demographic subtitle that characterise a rival - `--` still means a rank that could not be resolved and has to keep reading as one.
  `LiveReplayLeaderboardRow.rankedSkippingGhosts` is the one numbering implementation for every site that numbers a window: numbering by list offset instead drew a repeat climber's two rows as two number ones and showed every rival above the ghost a place better than they stood.
  That row is read straight by owner on every board (`fetchOwnPreviousCompletionRow`): the flagged bucket-zero entry once per session, then one document per bucket, held at its final steps once it is home.
  Gating that read on `collapsesRepeatFinishers` left the marker on a Just Climb drawn only while the ghost sat inside the eight-row page - the flicker the direct read exists to remove - so nothing about the live window consults that predicate.
  What a session learns about the climber's own published rows - the flagged best and the count of their attempts - is true for that session and no longer, so the repository keeps it in one uid-keyed slot that `beginLiveSession()` empties (the view model crosses that boundary before its first window refresh) and `clearAccountScopedCaches()` empties with the finisher set; nothing a rival publishes is cached.
  The finished-row diagnostic reports only `FAILED_PRECONDITION`, the missing-index refusal; losing signal fails the same reads with `UNAVAILABLE` and is neither reported nor allowed to spend the once-per-session budget.
- **A live surface never states an ordinal without the population it counted, and there are two states rather than three.** `LiveReplayLiveStanding` is what the live panel and the Live Activity both resolve, so the Lock Screen cannot disagree with the panel. `.racing` keeps the field-size line and puts the climber's own-climbs placing beneath it; `.alone` draws no leaderboard placing anywhere on the board - not in a rank cell, not on the Lock Screen - and the footer states `LiveReplayPersonalPlacing` alone ("2ND" over "OF YOUR 5 CLIMBS"). A bare ordinal is unrepresentable in the type on purpose: a climber alone on a tower was told `#1` with nothing on screen naming what the one counted, seconds before the finish card told them something else.
  `isSoleClimber` (`totalClimbers <= 1`) is the board's own answer and is never inferred from a missing field size - a routine board that can substantiate no count still has rivals on it. A first-ever climb on an empty board and a repeat climber alone on a tower are the same state and read the same.
  The placing counts the climber's own entries (every attempt of theirs, not the flagged one), so the collapsed race rows never have to answer a question they cannot: their second-best run is not on the board at all. Those reads are `userId`-scoped and carry their own declared indexes (`userId + stepsAtBucket`, and `userId + finalSteps + splitBucketCount` for the finished half); they reuse the one `finishedAhead` predicate rather than a second spelling of it, so a placing can never count rows the race did not. A first climb is `1` of `1` with no read at all, and a count that fails states no ordinal rather than a guessed one.
- Every replay context ranks the live climber against **one row per opponent - each opponent's best completion on that board**, "best" being the board's own ranking metric. Multiple completions by the same user collapse to their best for the live race; chasing a rival three times (their slow, middling, and fast attempts) is clutter, not competition. The static per-climb leaderboard separately preserves the full completion history (see `ascend-leaderboards`). Only target-reached completions feed a per-climb or routine context; an open Just Climb has no target, so it publishes on any stop that took steps (`hasCompletedJustClimbSession`).
- **Best-per-user collapse is server-owned and now runs on EVERY board.** Each bucket entry carries an `isBestForUser` flag, re-derived from the entries themselves whenever a workout publishes, changes, or is deleted (`seedBestForUser` / `reconcileUserBestEntries`). Live-race reads filter on that flag on all three context types; the static completion board reads the same entries unfiltered. Do not collapse repeats by filtering rows on the client: live rank and climber counts come from Firestore aggregation counts, which only a server-side filter can make count climbers instead of attempts.
  Settled by the captain on 2026-09-02: **all three board types race off one mechanism**, rather than one behaving differently because it is missing a piece of data. The flag used to be withheld from `just_climb` and `routine`, which is why an open Just Climb raced a rival's four runs as four opponents and showed a climber their own earlier attempts as racers - the collapse removing those is the ghost design, not a side effect.
  **`collapsesRepeatFinishers` no longer gates the flag**, so do not re-gate `seedBestForUser` or `reconcileUserBestEntries` on it. What that predicate still decides is stated once, below.
  **Known cost of that decision, recorded rather than argued away.** An open Just Climb has no step target, so on a duration metric a climber's shortest attempt is the one they quit earliest, and the collapse therefore represents them by their quickest session. The board already ranked every attempt that way, so this makes the field consistent with the metric rather than introducing the problem; the lever if it ever needs changing is the Just Climb ranking metric, not the collapse.
  **Ordering is load-bearing on release.** Firestore equality never matches a missing field, so a client build that filters on the flag renders every board whose rows predate it completely empty. Deploy the Cloud Functions first, run `scripts/backfill-live-replay-best-per-user.mjs` against every environment second, ship the iOS build third. That script mirrors the server's `ranksOnSteps` when picking a winner - it once picked on duration alone, which would have frozen the wrong row on a steps-ranked `routine_template` board the moment it stopped being `live_climb`-only.
- The flag itself is on no allowlist: every replay context type writes it and every live-race read filters on it, so a new context type inherits the collapse without a decision. "Best" is the context's ranked metric, and that IS per context type, all four of them: `routine_template` ranks on the highest-steps completion, because its intervals fix the clock and leave the steps to vary; `live_climb`, `just_climb` and `routine` all rank on the fastest completion. Do not reach for the step-target rationale to explain that grouping - a `live_climb` has a target and an open Just Climb has none at all, and they still share a metric. One predicate decides it on each side - `ranksOnSteps` on the server, `LiveReplayLeaderboardContextType.rankingMetric` on the client - and the seed and the backfill mirror it rather than picking on duration alone, which would freeze the wrong row on a steps-ranked board.
  `collapsesRepeatFinishers` survives as a much narrower allowlist - `live_climb` and `routine_template` - and decides two things only: what the SERVER's frozen standing counts, and which population a board's field-size line names (`fieldPopulation`). It does not gate the flag and it does not shape the live-race read. Do not re-gate either on it, and do not add `just_climb`/`routine` to it to make the boards agree: that silently changes write-once `completionSnapshots` arithmetic, which is a separate decision nobody has made.
- **The ranking metric is the server's, mirrored, and the two lists are not the same list.** `ranksOnSteps` in `functions/src/liveReplayLeaderboard.ts` is `contextType === "routine_template"` and nothing else, so a plain `routine` board ranks on the clock even though it is a routine and even though it sits outside `collapsesRepeatFinishers` alongside `just_climb`. `LiveReplayLeaderboardContextType.rankingMetric` mirrors exactly that, and `LiveReplayRankingMetricTests` pins it per context type.
  Getting it wrong is not a difference of opinion about ordering: the client's numerator counts finisher documents through `finisherBestField`, so naming `bestFinalSteps` on a board whose finishers only carry `bestCompletionDurationSeconds` matches zero documents and reports first place to every climber on it. That is the same zero-match failure as filtering `just_climb` entries on `isBestForUser`, relocated to another field, which is why the pin is per context type rather than per metric.
- **Every board that shows a field size names the population it counted.**
  Ascend counts three different populations of one climb on purpose - the live race panel collapses each rival to their best run, Climb Detail's board keeps every completion, and the completion hero freezes a standing - so a bare total made three correct numbers read as one broken one (#504).
  Both boards pin the same line beneath their rows (`LiveReplayFieldSizeLine` over a `LiveReplayFieldSize`): `27 CLIMBERS` live, `60 COMPLETIONS` static, and the completion hero's field line takes the same noun ("FASTEST OF 27 CLIMBERS").
  One shared treatment is the point: the moment the two lines differ, the two totals stop reading as two deliberate answers.
  The noun follows the number it is printed beside and is never hardcoded.
  `LiveReplayLeaderboardContextType.fieldPopulation` is the board's own population and derives from `collapsesRepeatFinishers`, so a race panel over an open Just Climb, which races every completed attempt, cannot claim to be counting climbers; `recomputedFieldPopulation` is what a standing the *client* recomputes counted, which is climbers on every board.
  A completion hero takes whichever of the two belongs to the basis it is showing (`LiveClimbSummaryRankHero.fieldPopulation(on:)`), because those two figures legitimately differ on a board that races attempts.
  A repeat climber alone on a board shows two rows - one climber, two of their runs - and that board states no field size at all: a field of one is `.alone`, so the footer is the own-climbs placing rather than the `1 CLIMBER` line that used to read as a contradiction beside two rows.
  A surface holding no count it can substantiate states no field size at all: a fetched window's total is the summary's distinct-climber count plus the live climber where they hold no completion yet, floored by that climber's own rank and by nothing else - and a routine session has nothing to pass at all, so it passes none.
  That denominator comes from the summary the same fetch already reads, never from a count over bucket-zero rows: counting rows made every window fetch of every live session pay a whole-board aggregation, and it counted a repeat climber twice, once as their stored best row and once as the `+1` for the attempt on the machine. Whether the climber joins the field is `currentUserIsFinisher`, asked directly of the `finishers` collection; it is never inferred from a field count.
  The line is the existing secondary white, never lime - lime stays reserved for the earned rank ordinal - and the live panel keeps the title `LEADERBOARD`.
  The explanation is the noun at the bottom of the board, not a renamed header or an explanatory subline; both were reviewed and rejected.
- Post-completion share / summary rank is computed against completed bucket-zero replay entries with `completedCount` as the denominator. Don't reuse in-session time-window rank or total-climber count for completed share surfaces.
- A completion summary shows one of two different measurements in its rank hero, and they are expected to disagree. The server's `completionSnapshots/{workoutId}` doc (mirrored by `liveClimbPublishStatuses` as `rankAtCompletion` / `completedCountAtCompletion`) freezes the standing *at the moment the attempt published* and never moves; a rank recomputed from today's rows is a *current* standing. The first finisher of a climb therefore stays frozen at rank 1 over a field of 1 forever while Climb Detail's "N completed" - a live aggregation count over bucket-zero entries - keeps climbing. That is not a bug.
- **A frozen standing over a field of one is never rendered as a rank.** The number could not fall - 8:12, 9:40 and 14:00 all produced "1st of 1 CLIMBER" - so on a slower repeat the card congratulated the climber for the run that had just beaten them. The captain locked the replacement on 2026-09-01: *the leaderboard rank takes the hero whenever a real field exists; when the climber is alone on the tower the hero states their placing among their own climbs; when both are true the leaderboard rank leads and the personal placing drops to the achievement row.* `PersonalClimbPlacing` is that ordinal, placed against the climber's own completions of the same climb, and 1st of your own climbs *is* a personal best - so no separate personal-best hero exists. A first finish with nobody else on the board spends the slot on the permanent thing instead: the gold flag and `FIRST ASCENT CLAIMED`, and nothing else. The ordinal is the accent in every case; only that claim is gold. `LiveClimbSummaryRankHero` makes the old pairing unrepresentable rather than wording around it, and until the climber's own history has been read the slot waits rather than falling back to the rank.
- **A climber's previous best on a tower is a marker, not a row.** It is a single vertical line inside their own row's progress fill at the position that best had reached, with `BEST` in vertical letters to its right - no rank cell, not tappable, never counted in the rank or the field size, and carrying no step count, time or gap sentence, because the visible distance between the fill's edge and the line is the whole message. The line never fades or restyles once passed; only the word fades, where it would collide with the row's trailing step count. `LiveReplayLeaderboardWindow.opponentRows` withdraws the row and takes it back out of the rank, which is why a solo repeat reads `1st` over a board of one climber instead of `#2`. The Just Me rail draws the same marker turned on its side, below the word, narrowed to the track. Pinned by `scripts/test/ranking-ghost-design-contract.test.mjs`, which fails if any deleted comparison number returns.
- **The frozen stamp counts whatever the board it sits beside counts, on both halves, by construction** (`readCompletionField` / `frozenCompletionStanding`).
  Settled by the captain on 2026-08-29: "1st of 5" on a Live Climb names five *people*, so a context that collapses repeat finishers counts **distinct climbers** on both halves - the numerator counts finisher documents whose stored best leads, the denominator is the distinct-finisher `completedCount`.
  An open Just Climb races every attempt as its own opponent, so both halves count attempts and the denominator is the published attempt count, plus this one where its row has not committed yet.
  **The rank is computed on the time of the climb it belongs to, never on the climber's all-time best.** Settled by the captain on 2026-09-01: "You use the time from the given climb for the rank. You don't use the all-time best for the rank." Every completion summary is a permanent record of the climb it sits on, so a 9:40 shows the rank a 9:40 earned and an 8:12 shows the rank an 8:12 earned on the day it landed, and the two do not have to agree.
  So the numerator counts finisher documents whose stored best beats **this attempt's own ranking value**, and then removes the climber's own leading row (`ownLeadingFinisherCount`).
  That subtraction is not a clamp and never was - it is the implementation of "a board with one row per climber must never seat someone behind themselves" - and `rank <= population` holds structurally because the others ahead can never exceed `population - 1`, so the throw above it is a safety net rather than load-bearing.
  Ranking a repeat on its climber's best instead reads as the generous fix and is worse than the bug it resembles: on a board where a rival's best beats this run, it tells the climber their slower run came *first*. A solo climber's "1st of 1" is arithmetically correct - a field of one climber genuinely places them first - and its defect is presentational only, owned by the finish-card hero rather than by this arithmetic.
  `readCompletionField` owns the whole numerator - the finisher document and the count over the same collection, at one moment - so the two inputs that decide the rank can never disagree with each other.
  The denominator is not its to own: `completedCount` is resolved inside the transaction, because `replaySummaryWrite` stamps that same number onto the summary Climb Detail reads as "N completed", and a frozen population that disagreed with it would put two answers about one field on two screens.
  So one residual race remains, and it errs in exactly one direction: another climber's *first* completion committing between the pre-transaction numerator and the transaction is counted by the denominator and not by the numerator, freezing a rank one place too good ("2nd of 4" where the field had placed them 3rd).
  It under-counts, so it can never trip the throw, and it needs a first-ever finisher landing inside that window on the same board. Do not close it by moving the denominator to a pre-transaction count - Firestore cannot aggregate inside a transaction, and a count taken outside it would drift from the summary's self-healing `completedCount`, which is `max(previous + 1, globalCompletionOrder)` rather than a plain tally.
  Count finishers, never entries flagged `isBestForUser`: that flag is one row per climber only *eventually*, because `publishReplayEntries` commits the improved row flagged true while the old row is still flagged true and `reconcileUserBestEntries` clears the old one many awaits later in the same trigger.
  A rival caught in that window counted as two climbers and silently inflated a permanent rank by one; the finishers subcollection is one document per climber by construction, written in the same transaction as the row it stands for, so there is no window to be caught in.
  **The client's recomputed standing counts finishers too, and it counts them on every board.** Settled by the captain on 2026-09-02: an open Just Climb ranks against unique climbers at their best, so a board with 41 finishes from 16 climbers where five distinct climbers beat the run reads "6th of 16" - never "13th of 16", never "13th of 41".
  Do not implement that by filtering entries on `isBestForUser`, even though every board carries the flag now. It is one row per climber only *eventually* (see above), and a permanent standing may not be frozen off a number that is briefly wrong. The flag is also newer than the rows: a board whose entries predate the backfill answers a filtered count with zero, and every climber on it would read "1st of 1".
  `finishers` is the field instead, on both halves and every context type - `finisherStatusWrite` is not gated on `collapsesRepeatFinishers` (measured: prod `just_climb__global` 2/2 finishers carry `bestCompletionDurationSeconds`, staging 898/898). No new field, no backfill, no server change.
  `fetchCompletionRank` therefore has one path: `countFinishersBetterThan` for the numerator, a count over the same collection for the denominator, and the climber's own stored best read from their own finisher document. Both halves out of one collection is the point - the row the count included and the row `ownLeadingRowCount` removes are the same row, so the subtraction can never leave a negative and render "#0".
  It counts finishers ahead of **this attempt's own value** and then removes the climber's own leading row (`ownLeadingRowCount`, the client half of `ownLeadingFinisherCount`), and the climber joins the field only when they hold no finisher document yet - a question about the climber, never about whether this attempt has published.
  Nothing clamps the pair back into agreement - a rank outside its own denominator means the halves counted different things, and `Math.min` only replaced one wrong permanent number with another (it reported "3rd of 3" for a climber the field had placed 6th).
  An impossible pairing throws on the server and the publish retries.
  Every numerator, client and server, is a single inequality on one field, which Firestore indexes automatically - so no composite index is declared for it, and no field override may ever strip `finishers.bestCompletionDurationSeconds` or `finishers.bestFinalSteps` of its default index.
  **Known open item: on `just_climb` and `routine` the recomputed standing and the frozen stamp now count different populations.** The server's `readCompletionField` still counts attempts on both halves there, which has no internal mismatch of its own; changing it is a meaning change to write-once `completionSnapshots` requiring a backfill, and that captain decision has not been made. So a `.current` standing on those boards reads "6th of 16 CLIMBERS" while the stamp that later replaces it reads "13th of 41 COMPLETIONS". The noun follows the basis (`LiveClimbSummaryRankHero.fieldPopulation(on:)`), so neither line names a population nothing counted, but the two figures do differ and that is expected until the server half is settled.
  **The live window does NOT take that split - it is one shape on every board.** `fetchWindow` resolves one `WindowStanding`: every ghost carries `isBestForUser` and so stands for exactly one climber, so counting the ghosts ahead at this bucket already counts people, and the summary's distinct-climber count is the field they were counted out of. Both halves count climbers, on all three context types.
  There was briefly a second case that ranked `just_climb`/`routine` mid-race off the finishers read `fetchCompletionRank` makes, against a synthesised "value the attempt would carry if it stopped at this bucket". It was deleted, and it must not come back. On a duration-ranked board that value is `bucketIndex * bucketIntervalSeconds` - the elapsed session clock, identical for every climber on the machine - so a climber started first and slid down as the seconds passed, with their performance playing no part. A finishers read answers a question about a *finished* attempt; a mid-race rank is a question about position in the field right now.
  Nothing floors that denominator with a count of the rows fetched. The rows on screen are a window, not a census, so sizing a whole-board total by how many of them fit puts a display artefact into a measurement. The only floor is the climber's own rank, so the pair can never read "3rd of 2". The rows stay a race view; the rank and the total are the standing.
- **Just Climb's summary counts climbers while Climb Detail lists every completion, and that is the design.** Accepted by the captain on 2026-09-02, in his own terms: Climb Detail is the full history of all the times, the rank card states CLIMBERS explicitly, and the two are therefore already disambiguated on screen - a reader who finds them counting different populations is looking at a deliberate design, not a defect.
  The noun is what makes that accept valid, so it is not cosmetic and may not be changed without reopening the decision.
  It is test-pinned at both ends for that reason: `LiveClimbSummaryRankHeroTests` holds the decision (`fieldPopulation(on:)` on a `.current` standing over `just_climb`/`routine`) and `LiveReplayFieldPopulationRenderEvidenceTests` reads the word back out of the rendered pixels. Both fail if `recomputedFieldPopulation` is ever tidied back into deriving from `collapsesRepeatFinishers`.
- **A seeded board needs finishers, not just entries.** `scripts/seed-live-replay-leaderboards.mjs` writes one finisher per synthetic attempt (`scripts/seed/lib/live-replay-finisher.mjs`) because the numerator counts them.
  A fixture board carrying entries and no finishers reads as an empty field and freezes a mid-field climber at "1st of 84"; clearing a seed pack has to take them back out, including wholesale on an open First Ascent climb whose fixture promises zero completions.
- Two invariants keep that legible, both held by `LiveClimbSummaryRankHero` (pure, unit-tested; the view only feeds it candidate readings). Rank and denominator resolve together from one source - a frozen position over a live denominator is a number that was never true. The hero enforces that for every source it resolves itself; for the standing a presenter hands in it is a trusted precondition it cannot check, and `LiveClimbSessionViewModel` can currently supply a window rank over a summary-wide total. And whenever the hero can name the population, the detail line does: "RANK WHEN YOU FINISHED" for the frozen basis, in both moments, "CURRENT LEADERBOARD RANK" for a recomputed one. Never let one basis borrow the other's copy; it invites a comparison the numbers don't support. The completion summary shows that detail line only where it cannot do better: `LiveClimbSummaryRankHeroView` states the ordering in plain language instead - "FASTEST OF 1,284 CLIMBERS", or the board's real ranking metric (`LiveReplayLeaderboardContextType.rankingMetric`) - and only where it holds a settled rank, a denominator, and a basis that is not `.liveSession`, because a field line asserts an ordering over a named population.
- **The frozen line reads the same in both moments, and there is no post-session tense to re-add.** It once said "RANK YOU JUST EARNED" on the completion moment and "RANK WHEN YOU FINISHED" on a look back. Both are true of the same number - the rank belongs to that climb's own time either way - so the second tense bought nothing and cost a branch: the `Moment` enum existed solely to swap it, so it was deleted with it rather than left as a no-op ternary over two constants the next reader has to disprove.
  What this does **not** fix, and what the wording was never going to fix, is a solo climber seeing "1st of 1 CLIMBER" on the **finish card** at all. The approved ranking-and-ghost design replaces that whole hero - alone on a tower you get no leaderboard rank, and the hero states your placing among your own climbs ("2nd" over "OF YOUR 5 CLIMBS"). The *live* surfaces already do exactly that (`LiveReplayLiveStanding`, above), so the panel and the Lock Screen no longer contradict the card; the finish-card hero, the ghost marker and the Climb Detail board remain owned by the `implement-ranking-ghost-design` task. Do not build an interim hero here; it would land the finish card ahead of the rail marker it was designed to pair with.
- The third basis, `.liveSession`, is the standing a live session computed against its own bucket-windowed race population (`ActiveRoutineViewModel` / `LiveClimbSessionViewModel` `completionLeaderboardRank`). Nothing can characterise that population after the fact, so it deliberately renders neutral session copy ("ROUTINE COMPLETE", "WORKOUT COMPLETE") rather than claiming a leaderboard basis. Keeping in-session window figures off completed surfaces entirely is tracked separately - until then, that basis is the seam, and nothing else may use it.
- The presenting surface declares the basis for the standing it passes in (`leaderboardRankBasis`); the hero never infers it from which slot a number arrived in. Only the caller knows what it measured - `ActiveRoutineView` declares `.liveSession` for the window rank it computed itself, while `WorkoutDetailView` hands in no rank at all and lets the summary resolve one, declaring `.current` for the fallback that lands in that slot. Wire a new presenter by deciding its basis, not by copying a neighbour's.
- A frozen standing is also **permanent and read once**. `FrozenCompletionRankStore` (UserDefaults, wiped by account deletion) keeps the server's `completionSnapshots` answer on device, and `CompletedClimbRankService` is the single read path: it serves the stored value synchronously, fetches at most once per workout, coalesces concurrent callers, and never overwrites an already-frozen record. A reopened completed-climb summary therefore settles on its final rank without issuing a request - no snapshot read, no publish poll, no recomputation. Never write a client-recomputed rank into that store; only a server-authored snapshot is frozen. Live surfaces (the live session leaderboard, Climb Detail's board) deliberately do not read it and keep re-reading the server.
  A saved climb's share card reads the same store through `SavedClimbShareStanding`, seeded on the Share tap from what the device already holds and falling through to one read only for a workout this install has never resolved - so Workout Detail and the summary cannot disagree, and a session the server ranks nowhere costs nothing to open.
- The rank slot holds a rank, a loading treatment (`AscendSkeletonText`, the shared head-to-head pattern), or nothing - never a status word. "Complete" or "Checking" where "21st" goes reads as a load that never finished. `LiveClimbSummaryRankHero.Value` makes that unrepresentable, and a session that ranks nowhere renders no hero at all rather than a placeholder. "Nothing" is reserved for a *settled* lookup: `RankResolution` distinguishes `notStarted` from `settled`, so the frame before the lookup starts loads instead of asserting the terminal "CHECK LEADERBOARD LATER".
- Which board a finished session ranks on is decided by `LiveClimbWorkoutSummaryData.leaderboardContext`, which reads the stored `climbId` first and `trackingMode` only as a tiebreak. `trackingMode` shipped after the first Live Climbs, so reading it first strands those early workouts with no leaderboard at all.
- Step timeline checkpoints are source-neutral. Sensor producers emit cumulative step samples into a shared recorder so result / replay UI doesn't depend on one sensor source.
- Heart-rate samples are checkpointed onto the active draft the same way step data is, and each sample is stamped on the *logical* workout timeline (draft start + the resume-inclusive elapsed clock), never on wall-clock time. A resumed or recovered session therefore extends one continuous series instead of restarting it, and saving straight from recovery keeps the pre-interruption trace. Never clear the buffer on resume. The saved workout carries `HeartRateTraceCoverage` in its source metadata so a genuinely partial trace can't read as a complete one.
- The replay index is server-published - clients write zero leaderboard data during a live session. A Cloud Function publishes from saved attempts after the session ends and normalizes degenerate curves (e.g. all-zero-until-final-bucket) into conservative monotonic curves so replay rows don't appear stationary.
- That normalization exists twice - `LiveClimbWorkoutSummaryData.normalizedSplitSteps` (Swift) and `functions/src/liveReplaySplitNormalization.ts` - and both are pinned by `SharedTestVectors/live-replay-split-normalization-vector.json`. The end-anchored bucket contract they share is stated on `LiveReplaySplitCurve`; don't restate it elsewhere or author a third normalizer.
- Replay rows denormalize public display fields (display name, avatar token, optional photo URL) so live-session client code does not read private user documents during a race.
  For real users those stored fields carry validated account-authored identity or the stable UID-derived fallback.
  Rows with the server-owned `isSynthetic` marker keep authored fixture identity, account deletion keeps the `Anonymous Climber` sentinel, and clients apply the shared moderation resolver before rendering (see `ascend-profile`).
- Per-climb rank and total-climber counts stay hidden until real backend data exists. No placeholder public stats.
- Future demographic / peer-group insights must use declared profile fields and stay opt-in / privacy-safe.

## Apple Health enrichment
- Apple Health can *enrich* a saved Live Climb workout with the metrics it did not capture itself: heart rate (average, maximum, series) and calories. It must never become the canonical Live Climb source.
- **Heart rate and calories do not need an Apple Health workout at all.** `AppleHealthEnrichmentService` owns that path and reads `heartRate` / `activeEnergyBurned` quantity samples over the climb's own time window.
  HealthKit normalises those regardless of writer, so Garmin, Whoop, Polar, a chest-strap app and Apple Watch all arrive through the one path - never branch enrichment on device, and never let copy name one wearable.
  What genuinely differs between them is sample density and whether the device wrote anything, so a sparse series is a real answer that ends the retry series, not a failed read.
  There is no matching step and no foreign workout record is read or written; Apple Health workout import was deleted with #437.
- **Enrichment retries on a bounded persisted schedule, because one read at save time races the wearable and loses.** Health had published nothing yet, so enrichment found nothing and never looked again (#438).
  `AppleHealthEnrichmentSchedule` is the curve (nine attempts reaching ~10h), `AppleHealthEnrichmentAttemptStore` persists eligibility as an absolute date so the budget survives relaunch and several callers asking at once cannot spend it in one instant, and one timer serves every tracked climb rather than one per climb.
  The service is an `AuthenticatedSessionWorker`, so sign-out and account deletion stop it; re-arming happens on authenticated bootstrap and on foreground, because a suspended app's `Task.sleep` is not an alarm clock.
  Regression coverage: `AscendAppTests/AppleHealthEnrichmentServiceTests.swift`.
- Automatic retries are additionally bounded by a window measured from the end of the workout (currently 72h).
- **The completion summary and Workout Detail are show-or-hide.** A stored heart-rate series renders its chart; no series renders nothing at all - no heading, no card, no explanation, no empty state - while enrichment keeps looking underneath. Workout Detail's remote-series restore state stays, because it means data exists and is arriving.
  Settings -> Integrations is the only Apple Health connection and revoked-access surface, and nothing here may resolve a per-climb Health status to narrate. Contract and coverage: `ascend-apple-health-enrichment`.
- Enrichment preserves the Live Climb's source, steps, floors, duration, and attempt participation - it only adds heart rate and calories.
- Enrichment is **silent** about its *results*. An enriched Live Climb never asks the user to confirm or edit the merged data. If the data arrives after the completion summary has been dismissed, it shows up on the workout detail next time the user looks - no notification, no review.
- The user gathers notes / media for a Live Climb at the **completion summary**. Nothing about enrichment's *results* may interrupt that moment.

## Climb content (catalog + images)
- When adding, editing, releasing, or validating Live Climb catalog content, use the `live-climb-content` skill. That file is intentionally harness-neutral so Codex, Claude, Cursor, or any other AI provider can follow the same workflow.
- Climb content is remote-first by default. The catalog ships as a hosted manifest + versioned catalog file; climb images live in Storage as hero / card / thumb sizes. Adding a new climb means publishing new content, never shipping app code (see Content-driven over rebuild in the core guide).
- A bundled bootstrap catalog ships with the app for *metadata only*, so Home and Browse render even if the remote catalog has never been fetched. Once a remote catalog has been successfully fetched, subsequent launches prefer the disk-cached catalog over the bundled bootstrap.
- Climb images do not ship in the app bundle - artwork is remote-only. Missing images render a placeholder until the remote image is cached locally.
- Catalog and image fetching use shared disk-backed cache infrastructure. Climb-specific fetch/decode logic stays in climb repositories; the cache layer is generic.
- Home, Browse, and Detail render from cached / local state first, then refresh remote content in the background. Don't block UI on network fetches.

## Climb card visual treatment
- Reusable climb card surfaces share common chrome (split-card surface, leading artwork, animated tier border). Don't reimplement split layouts, image clipping, or tier-border animation per screen.

## Catalog Release Phasing
- Catalog release state is server-controlled. The app model currently uses `releaseState`; if a remote content feed exposes `releaseStatus`, map it into the same release-state domain instead of branching UI on a second concept.
- Launch composition should be content-driven: available climbs, coming-soon climbs, hidden climbs, and disabled climbs are all catalog data, not app-release code paths.
- New climb drops should be publishable by changing hosted catalog data and image assets. Avoid adding per-climb code, hardcoded IDs outside smart defaults, or app-store-release dependencies for catalog expansion.
- First Ascent availability follows release phasing: hidden and disabled climbs do not appear as open First Ascent opportunities; coming-soon climbs can tease future drops but must not accept live attempts until available. A First Ascent already *held* on a hidden climb still renders - only the unclaimed slot needs `available` (`ProfileFirstAscentService`).
- Coming Soon climbs follow a cross-surface mystery pattern. The Pokedex shows blurred silhouette only (no name, no location). The Globe shows location only (via dim pin with region revealed on tap). The user pieces together identity by cross-referencing both surfaces; neither reveals everything on its own.
- All climb tiers use the same rotating tier-border treatment driven by per-tier color tokens. Mythic is the emphasized tier (strongest glow, purple-forward prismatic palette).
- Persistent idle climb surfaces (e.g. the Home daily card) may use a lighter ambient border treatment with an unblurred moving highlight to reduce per-frame animation work while preserving visible motion.
