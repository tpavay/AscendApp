# Web + Email

Website source lives in `web/` (Astro) and is built to `web/dist/` before deploy. Load `firebase-hosting-basics` for hosting/rewrite/deploy work.

## No public unauthenticated endpoints
The waitlist signup endpoint, its Beehiiv integration, and the public IP rate limiter were removed in #330: a live `POST /api/join-waitlist` with no form anywhere behind it was attack surface for no benefit.
Cloud Functions now expose exactly one unauthenticated HTTP route, `/api/unsubscribe`, and it acts only on `POST` with a valid HMAC token.
Adding another public endpoint means re-introducing abuse controls that no longer exist in this repo - decide that deliberately rather than by reflex.

## Transactional email
- Transactional emails for feedback and product triggers must be sent server-side from Cloud Functions, never directly from the website or iOS client.
- Cloud Functions email provider config lives in the `TRANSACTIONAL_EMAIL_CONFIG` Secret Manager JSON secret, with `functions/.secret.local` used only for local emulator overrides.
- `TRANSACTIONAL_EMAIL_CONFIG.unsubscribeSigningKey` is **required** (min 32 chars) and signs unsubscribe tokens. A missing or short key makes `getTransactionalEmailConfig()` throw, which fails every transactional send, so add the key to each environment's secret *before* deploying functions. It fails loudly by design: mail must never go out without a working opt-out path. Rotating the key invalidates unsubscribe links in already-delivered mail, so treat it as long-lived.
- `TRANSACTIONAL_EMAIL_CONFIG.websiteUrl` is **required** and must be an https URL, and carries the same before-deploy secret-ordering requirement as `unsubscribeSigningKey`: set it in each environment's secret *before* deploying functions or every transactional send fails. It is required rather than defaulted because it is the host the unsubscribe link points at, and the token in that link is signed with the *current* environment's key. A silent fallback to the production host would make staging emails carry links that verify against the production key and never work.
- Queued transactional emails are delivered in the background by the scheduled `processEmailJobs` worker. `onLifecycleEventEmailAutomation` (rating prompt) and `weeklyRecapEmails`/`monthlyRecapEmails` (`functions/src/recapEmails.ts`) are its producers, as is the operator-run `scripts/send-drop-email.mjs` (`functions/src/dropEmails.ts`), and every one of them stamps a `recipientUid`.
- Every producer enqueues through `enqueueLifecycleEmailIfAllowed` (`email/queue.ts`) rather than hand-rolling the dedupe-check-then-write transaction: one job-id-exists check plus one `isLifecycleEmailAllowed` consent read, in the same transaction as the write, so a concurrent producer can neither double-queue nor slip past a stale preference read. Add a new lifecycle-email producer by calling this, not by copying the transaction.
- `createQueuedEmailJob` strips any payload field left `undefined` before writing - Firestore's `set` refuses a document containing a literal `undefined` anywhere in it, and a payload interface with an optional field (no rank moment this period, no comparison to a prior period that does not exist yet) will genuinely have one on the common case, not the edge case. This one choke point is what makes every payload safe to build with plain `field: maybeUndefinedValue` object literals; do not reintroduce a `JSON.parse(JSON.stringify(...))`-style workaround at a call site.
- A queued job outlives the build that wrote it, so `renderEmailContentForJob` names an unmapped type (`unsupported_email_type:<type>`) rather than faulting on an undefined catalog entry. Keep that guard when retiring an `EmailType`; `functions/test/emulator/emailQueue.test.ts` is the regression, and it also asserts a leftover job of a retired type does not stop the live job beside it in the same batch.
- In-app feedback submissions (`feedback` collection) trigger `onFeedbackCreated`, which sends an admin notification email directly via Resend (not queued). The recipient is `feedbackNotificationEmail` from the secret config (falls back to `replyTo` -> `fromEmail`). Reply-to is set to the submitting user's email. Notification delivery metadata is written back onto the feedback document.

## Weekly / monthly recap emails
- **One composition, two channels.** `functions/src/recapEmails.ts` owns four scheduled functions.
  `composeWeeklyRecaps` (Monday 00:30 UTC) and `composeMonthlyRecaps` (the 1st, 00:30 UTC) write `users/{uid}/recaps/{cadence}_{periodKey}` for the period that just closed: `active` for every climber ranked that period, `inactive` for every climber who has climbed before but not then, and `never_climbed` for every `app_access` holder who has never climbed.
  `docs/champion-recognition.md` owns every field of that document.
  `weeklyRecapEmails` (Monday 13:00 UTC) and `monthlyRecapEmails` (the 1st, 13:00 UTC) keep their deployed names and schedules but only *send*: they read the stored recaps back through a collection-group query on `cadence` + `periodKey` (the composite index lives in `firestore.indexes.json`) and map each one onto `RecapActivePayload` / `RecapInactivePayload` through `buildActiveRecapEmailPayload` / `buildInactiveRecapEmailPayload`, so the app and the email can never disagree.
  Send never composes: a period with no stored recaps logs `recapEmails.recapsMissing` at error level and sends nothing.
  Compose writes for every climber whether or not they have an email address; the email-address check, the consent gate, the dedupe key and the zero-activity suppression all live in send.
  A `never_climbed` recap is app-only - that gap belongs to the onboarding-abandonment emails, so it never produces an email.
- **Compose is create-once and waits for the finalizer.** A recap is written with `create()` after an existence read, so a re-run skips everyone already done and can never reset a `seenAt` or re-rank a climber after a late sync.
  The award rank is read from the achievement record `finalizeLeaderboardAchievements` writes at 00:15 UTC, so compose first checks `leaderboard_periods/{cadence}_{periodKey}.status == "finalized"` (committed in the finalizer's last commit, once every achievement has landed).
  Unfinalized within an hour of the close, compose writes nothing and throws, and the schedule's retry config (every ten minutes, five times) tries again; past the hour it composes anyway and logs `recapEmails.composedBeforeFinalization`.
  A run that failed some climbers also throws after writing everyone else, so the retry picks up exactly the failures.
- **The stored values are raw, and the email derives its chips from them.** `active` carries counts, prior-period counts (null, never zero, when there was no prior row), the award rank, and First Ascents as `{climbId, name}`; the delta chips, the Top 10 / Top 100 badge and the First Ascent badge are built at send time from those values, never stored.
  `climberCount` is stored only above one, and send reads a missing one back as a field of one, which is exactly the email the recap always sent.
- **Design (captain, 2026-09-24, Wispr-Flow-inspired layout in Ascend's own dark/green brand - never Wispr's colors, mascot, or copy; round 3 same day refined the content; round 4 same day was a captain review of the actual rendered emails; round 5 same day added real achievement badge artwork):** a bespoke dark-themed template family in `email/templates.ts` (`renderRecapActiveEmail`/`renderRecapInactiveEmail`, not the shared light `renderBrandedEmail` layout every other lifecycle email uses). Bold editorial hero titled "Your week/month on the stair stepper" (two words - round 4: "'your week on the board' sounds stupid") with the concrete dated period, leading with the climber's **rank and percentile shown together** as the hero's lead metric, then an optional row of earned achievement badge artwork, a 2x2 stat card grid with green "up only" delta chips against the prior period, and a per-day activity calendar heatmap (table-based, Monday-aligned, peak/active/none coloring). **There is no milestone-unlocked callout** - round 4 removed it entirely ("I don't like the whole milestone unlocked thing. That doesn't make any sense.") and `isMilestoneRank`/`pickMilestoneText`/`RecapActivePayload.milestoneText` no longer exist; do not re-add a milestone concept without a fresh captain decision. Copy is past tense throughout ("last week" / "last month") since every send lands after the period it describes has already closed - except the zero-activity subject lines, which are forward-looking CTAs about the new period, not descriptions of the closed one, and are correct as-is.
- **Round 4 color system, and why it changed:** the captain's read of the round-3 rendered emails was "it just looks flat... I don't know if it's the colors or if the calendar just doesn't look good. The boxes don't look good." The fix was replacing flat one-off hex constants with an opacity-derived system matching the app's own dark-theme tokens: true-black `#000000` base (`RECAP_BG`, matching `ThemedBackground`'s `Color.black`), `rgba(255,255,255,0.05)` card fills, `rgba(255,255,255,0.10)` borders, plus a `box-shadow` (`RECAP_CARD_SHADOW`, inset highlight + outer shadow - Outlook ignores it gracefully, a fine progressive enhancement) on every stat card and callout box for depth. A podium rank (`rank <= 3`) switches the rank-hero box and its percentile badge to the reserved gold medal token (`RECAP_GOLD` `#D4AF37`, `RECAP_GOLD_BG`, `RECAP_GOLD_BORDER`) instead of the green accent - the design system's sanctioned podium/rank-prestige exception, same rule as everywhere else in the app. The calendar's "No activity" legend swatch also got a border (`RECAP_BORDER`) - at the new low-opacity fill it was reading as invisible against the card background, which was part of the "boxes don't look good" complaint.
- **The zero-activity email is a real elapsed gap plus First Ascents, not a generic "the board missed you".** Round 4 ("the board miss you that doesn't make any sense... it should say 'We missed you'... 'We haven't seen you in 2 weeks'... maybe list first ascents, or if there aren't any, tell them to get started on a different climb") replaced the old generic subject/body with: subject `We missed you` (same for both cadences); body leads with the real gap (`gapCount` weeks or months, always ≥1, `weeksSince`/`monthsSince` in `recapEmails.ts`, measured against the compose run's clock and stored); then either lists every landmark the climber holds a permanent First Ascent of (`firstAscents`, sourced from `live_replay_leaderboards` where `firstAscentUserId == uid` - the durable record `liveReplayLeaderboard.ts` writes, not re-derived) or, if they have none, the existing suggested-comeback-climb nudge. `gapCount`'s source is the climber's latest workout `startedAt` before the period's end (one `orderBy("startedAt", "desc").limit(1)` read per zero-activity climber at compose, stored as `inactive.lastClimbAt`), never the `all_time` row's `lastUpdated`, which every reconcile restamps; at send, a fresh read of the latest workout at or after the closed period's end means the climber already came back, so the email is suppressed while the app keeps the recap. It falls back to the closed period's own start date only when no workout is found. A First Ascent the catalogue cannot name is dropped from `firstAscents`, while the active recap's `landmarksFinished` keeps an unresolved climb's raw ID so the count stays right. `RecapInactivePayload` carries `gapCount`/`firstAscents` now, not the old `inactiveHeadline`/generic-only shape.
- **The cohort split never scans `users` or a climber's full workout history.** `leaderboard_stats` already carries one document per `{user, timeFrame, period}` with a period's totals, and a period with zero workouts gets no row at all (`leaderboardStats.ts`'s `deriveLeaderboardRows`). So the ACTIVE cohort for a closed period is exactly the rows at `{timeFrame, periodStartAt}`, and "has ever climbed" is exactly the rows at `{timeFrame: "all_time"}` - zero-activity is the set difference, computed in memory from two cheap paginated scans (`pageLeaderboardStatsRows`, cursor by `FieldPath.documentId()`, no manual composite index needed, and a loud `logger.error` if the page bound is ever actually hit rather than a silent truncation). Each climber then costs exactly one bounded workout read: an active climber's is a field-projected (`.select(...)`, never the heart-rate series) `startedAt` range query bounded to the single closed period, to resolve landmark completions and the daily calendar; a zero-activity climber's is one indexed `orderBy("startedAt", "desc").limit(1).select("startedAt")` read of their latest workout for the real gap (`fetchLatestWorkoutStartedAt`), so the zero-activity gap is not free - and send repeats that latest-workout read once per zero-activity recap, unbounded by the period, because "already came back" is a fact about 13:00, not 00:30. If the active-cohort scan hits its page bound, compose writes nothing for that period (`recapEmails.sweepSkipped`) - a rank computed against an arbitrary partial cohort would be stored for good and emailed under a permanent dedupe key. `never_climbed` is the third scan: live `users/{uid}/entitlements/app_access` grants, read through the `accessUntil` collection-group index the expiry sweep already uses. If the `all_time` scan hits its bound, every `never_climbed` recap is withheld (`recapEmails.neverClimbedSkipped`), because a veteran past the cutoff would otherwise be told, permanently, that they have never climbed.
- **Rank and percentile are computed in memory, shown together, not read from an achievement doc.** `rankActiveCohort` ranks the already-loaded active cohort (mirroring `leaderboardAchievements.ts`'s standard competition ranking, 1-2-2-4, and its exclusion of zero-step rows, uncapped) - free, since the whole cohort is already resident for the active/inactive split. Round 3: the concrete rank (`#N of M climbers`) is *always* shown whenever the field is large enough to mean anything (`fieldSize > 1` - "1ST OF 1 CLIMBER never appears" applies here too); `percentileBand` is a separate, optional badge alongside it ("Top N%"), present only when the rank actually reaches one of the locked 1/5/10/25/50% bands.
- **Achievements are real badge artwork, reusing the app's own catalogue and one existing tracked concept - never re-derived, never invented.** Round 5 (captain, reviewing the round-4 emails: "we should include our achievement badges that we have in the app - if you were top 10, if you were top 100, if you got any first ascents") replaced the old text-only "Achievement earned" callout with `RecapEarnedBadge[]` (`email/types.ts`) rendered as real `ProfileAchievementCatalogue` artwork (`renderAchievementBadgesHtml`/`renderAchievementBadgeCardHtml` in `templates.ts`). `fetchAchievementRank` reads the same `users/{uid}/achievements/global_steps_{cadence}_{periodKey}` document `finalizeLeaderboardAchievements` (`leaderboardAchievements.ts`) already writes and returns just the rank; `buildRankBadge` (`recapEmails.ts`) collapses it to exactly the two badges the captain named - "Top 10" for any rank 1-10 (the app's own cumulative counting: a Top 1 or Top 3 finish also counts toward Top 10) and "Top 100" for 11-100 - deliberately no Top 1/Top 3/podium-medal badge, since the rank hero above it already states the exact placement. The active recap adds a **period-scoped** First Ascent badge via `buildFirstAscentBadge`, built from `fetchFirstAscentRecords`'s `firstAscentWorkoutId` matched in memory against the closed period's completed-landmark workouts that `fetchPeriodWorkoutDetails` already read (no second Firestore query, no new composite index), and the lookup runs only when that period holds a completed landmark. It keys on the claiming workout's `startedAt` window, never `firstAscentCompletedAt` - that is the server's processing time, which a late sync pushes into the next period - so the badge is always a subset of landmarks finished, and a climber who merely re-climbed a landmark they first-ascended earlier is never told it was new. A landmark the catalogue cannot name keeps the badge but drops its detail line. The inactive email's badge is the same helper over its existing lifetime-scoped `firstAscents` list. No callout (and no badge row) renders with an empty `earnedBadges` array. Do not invent a new achievement type or re-derive rank from the recap's own `rankActiveCohort` standing (a different, uncapped, potentially-larger-cohort ranking than the finalizer's own top-250 read).
- **Badge artwork is copied, not re-hosted from the app bundle, and needs a white backing plate for legibility.** The three PNGs live at `web/public/images/badges/{top10,top100,first-ascent}.png`, resized (`sips --resampleWidth 240`) from the real `AscendApp/Resources/Assets.xcassets/Images/{LeaderboardTop10,LeaderboardTop100,FirstAscentBadgeDetailed}` assets to keep the email light (27-43KB each vs. 130-365KB originals) - re-run that resize if the app's source art ever changes, there is no build step that syncs them. `recapBadgeImagePath` in `templates.ts` maps a badge id to its path, referenced through `getMarketingWebsiteUrl()` exactly like the header icon. `ProfilePrestigeBadgeArtwork` draws this art on no background at all in the app (dark chrome text with a thin glow, meant to sit on the app's own black canvas), which reads as almost illegible against this email's gold-tinted or translucent card fills - `renderAchievementBadgeCardHtml` wraps just the `<img>` in a small solid-white rounded plate so the artwork keeps its contrast regardless of the card behind it; do not remove that plate as "matching the app more closely" without checking actual rendered contrast first. Top 10 and First Ascent badges use the reserved gold "rank-prestige" card token (`RECAP_GOLD_BORDER`/`RECAP_GOLD_BG`), matching `ProfileAchievementCatalogue`'s own gold tint for those two; Top 100 stays on the neutral card treatment, matching the catalogue's secondary-text (gray) tint for that one badge.
- Delta chips (`buildDeltaChip`) are built only for a genuine improvement over the prior period - never a decline or an unchanged figure - so the recap can never read as a scolding.
- **"Landmarks finished" uses `climbCompletions.ts`'s `parseCompletedLandmarkWorkout`** (the single definition of "finished a landmark" shared with Swift and the backfill), not a bare "carried a `climbId`" check - an abandoned Live Climb attempt is never reported as finished. This was a real bug caught by `no-mistakes` review before ship.
- Streak has no server field to read (`Workout.calculateWeeklyStreak` is client-only, over local-timezone SwiftData); the weekly recap reimplements it against UTC-Monday `leaderboard_stats` weekly rows, walking back from the closed week until the first gap.
- **The weekly period label is a concrete, dated range with the year** (`formatWeeklyPeriodLabel`, round 3: "Sep 15-21, 2026"), matching the monthly label's concreteness ("September 2026") - handles a week straddling a month or year boundary, though the common case never does. Do not revert to a bare "Sep 15 – Sep 21" with no year; a later reader needs to know exactly when it was.
- The suggested climb in a zero-activity email is the shortest currently *available* climb off the same hosted catalogue `announceClimbDrops` reads (`climbDropNotifications.ts`'s `makeHostedClimbCatalogSource`/`availableClimbIds`/`referenceStepCount` - reused directly, not reimplemented) - one pick per run, not personalized per climber. Named in copy only, never linked - see CTA below.
- **The CTA in every recap email is the App Store listing** (`https://apps.apple.com/app/id6757202987`, Ascend's production App Store Connect app id - `data/app-setup-runbook.md`), not a deep link into the app: no `/app/...` hosting route or universal link exists yet, and an earlier draft that linked there 404'd for every recipient (caught by `no-mistakes` review before ship). Upgrading to a universal link is a later, separate change.
- The dedupe key (`buildRecapDedupeKey`) is `{cadence}-recap:{periodKey}:{uid}` - shared by both the active and inactive variant, not namespaced per variant, so a late-synced workout that moves a climber from the inactive cohort to the active one between a sweep and its retry for the same closed period cannot earn them a second recap.
- Per-recipient composition and enqueue runs with bounded concurrency (`runWithBoundedConcurrency` from `concurrency.ts`, the same helper `climbDropNotifications.ts` uses), not sequentially - a large cohort must not run the 540s `onSchedule` invocation out the clock and silently strand the rest of a period's recipients, since a timed-out scheduled function is not retried.

## Drop announcement emails
- **One type, content on the job.** `drop_announcement` renders whatever `DropEmailPayload` (`email/types.ts`) carries - hero, banner, facts, item groups, CTA - through `email/dropTemplate.ts`, so the deployed worker draws a new drop without a new build. A drop's content lives in `email/drops.ts` (`DROP_EMAILS`); the Halloween 2026 one is the round 13 art direction (approved 2026-10-02).
- **Worded to the approved Halloween redesign (2026-10-02).** The October page's headline and subline, all 15 items in its three groups (climbs, steps, days), the redesign's names ("The Giant"), bare-count thresholds ("5 climbs", "10K steps", "31 days", "Climb on Oct 31"), and the ruling that every climb saved in October counts from October 1. No rarity or "Legendary" treatment: the redesign removed rarity from the app. `catalogueRequirement` produces that wording from the hosted catalogue, so the send script checks the email against it.
- **Readable with pictures blocked.** Many clients block remote pictures by default, and Gmail never loads them in Spam - which is how the first staging test looked broken. Every `<img>` carries fixed pixel dimensions, a fill and styled alt text inside a fixed-height well; the brand mark is a background image on a black cell, so a blocked logo leaves the ASCEND wordmark rather than a broken icon. `test/dropEmails.test.ts` holds that contract. The hero is a short 900x420 crop with no number in it, so the headline is in the first screen on a phone and in desktop Gmail.
- **The footer's postal address** comes from `SENDER_POSTAL_ADDRESS` in `email/drops.ts` and is left out while it is null; whether and which address Ascend publishes is the captain's call, so nothing refuses a send without one.
- **Built for Gmail, Apple Mail and Outlook.** Tables and inline styles only, no `<style>`, positioning, flex/grid or SVG; every colour a solid hex (Outlook on Windows drops rgba, so the mock's translucent borders are pre-blended over the surface they sit on); gradients, glows and the cobweb motif are progressive enhancement over a solid `bgcolor`; the hero's fade is baked into the JPEG. `test/dropEmails.test.ts` holds those rules.
- **Images are served from the target's own site** (`images/drops/<dropId>/` under `web/public`, the item thumbnails copied from the app's `Assets.xcassets/Gear`), and `assetBaseUrl` on the payload names that site. A test may point it at a hosting preview channel; a real send may not.
- **Sent by an operator, never by a schedule.** `scripts/send-drop-email.mjs` (dry run by default, `--preview`, `--test-to`, `--send`, `--status`) queues through `enqueueLifecycleEmailIfAllowed`, so consent is the same explicit-yes gate as every lifecycle email, checked again at send time. The dedupe key `drop:{dropId}:{uid}` makes a rerun queue only climbers not already queued; a test uses `drop-test:...` with a per-run suffix, so it never spends the account's real send.
- **`--send` refuses until the drop is true.** Every image must answer 200; every item, requirement and event must match the unlock catalogue that project's app reads (`catalogueRequirement` ports `UnlockCopy.requirement`), with no live event item left out; and in production the App Store must report at least the drop's `minimumAppStoreVersion`, because the email must not land before the update that contains what it promises.
- **The audience is the consent record, nothing else.** One collection-group read of `communication_preferences`, then one profile read per opted-in climber for `users/{uid}.email`. `processEmailJobs` delivers 25 a minute.

## The delivery outage, and the stale backlog
Until 2026-10-02 no environment's `TRANSACTIONAL_EMAIL_CONFIG` had an `unsubscribeSigningKey`, so `processEmailJobs` threw on its config assert every minute and no queued email was ever delivered; production held 6 queued jobs dating back to 2026-08-12.
Dev (version 4) and staging (version 3, pinned) now carry a key, and their `websiteUrl` names their own `https://<project>.web.app` so a non-production unsubscribe link reaches its own endpoint; it used to name the production site.
Production still has no key. Before adding one, run `scripts/skip-stale-email-jobs.mjs` (dry run, then `--commit`) against production with a cutoff of now, or the worker delivers the whole backlog - months-old recaps - the minute the key binds.

## Champion push
- `onLeaderboardResultCreatedChampionPush` (`functions/src/championPush.ts`) answers the creation of `leaderboard_results/{resultId}` with one `champion_crowned` push to every uid in `championUserIds`.
  It pushes only for `source == "leaderboard_finalizer"` and a period that closed within the last 48 hours, so a backfilled result, or an event retried long after the crowning, never pushes.
- **At most once per champion per result.** Every read happens first; then `_champion_push_deliveries/{resultId}_{uid}` is `create`d (fields `resultId`, `userId`, `createdAt`, `sentCount`, `status`), and an existing marker means skip.
  A send that throws after its claim is marked `status: "unsent"` and never retried; a second crown alert is the failure that cannot be taken back.
  The trigger is `retry: true` and throws while any champion is still owed an attempt - their placing is not written yet, or a read before their claim failed - and every champion already claimed is skipped on the retry.
- **Who.** The champion's `pushChampionCrownEnabled` (absent means on; `updatePushNotificationPreferences` takes an optional `championPushEnabled`, and a request must carry at least one of the two booleans) and their active iOS devices whose root `notification_devices` registration still names them and reports a deliverable authorization (`isDeliverableAuthorizationStatus`, shared with the climb-drop audience).
  The climb-drop toggle is not consulted, and dead tokens go through the shared `deactivatePushTokensByHash`.
- **Copy.** Title `You took the crown.`; body `Week {n} champion. {steps} steps. Defend it this week.`, `{Month} champion. {steps} steps. Defend it all month.` or `{year} champion. {steps} steps. Defend it all year.`, with the week number and month read from the period key in UTC and the steps from the champion's frozen placing.
  Data payload `{type: "champion_crowned", timeFrame, periodKey}`; the shipped router ignores any type it does not know.

## Unsubscribe & communication preferences
- Every user-addressed email carries RFC 8058 one-click `List-Unsubscribe` headers plus a footer unsubscribe link, both derived from the job's `recipientUid`. Admin feedback notifications have no `recipientUid` and intentionally get neither.
- The unsubscribe endpoint (`/api/unsubscribe` hosting rewrite to `unsubscribeFromEmails`) answers GET with a confirmation page and only acts on POST. Keep that split: link scanners and mail-client prefetchers follow GETs, and a GET that unsubscribes would opt users out without their knowledge.
- `users/{uid}/communication_preferences/current` has three writers: `recordLifecycleEvent` (email prefs), `updatePushNotificationPreferences` (push prefs: `pushClimbDropsEnabled` and `pushChampionCrownEnabled`), and `unsubscribeFromEmails` (the email unsubscribe endpoint). Any write to it must merge, or one feature silently clears the other's preference. `recordLifecycleEvent` and `unsubscribeFromEmails` merge by passing `{merge: true}` and building the document through the shared `buildNextCommunicationPreferences` helper; `updatePushNotificationPreferences` does not pass `{merge: true}` and is safe only because it does a transactional read-modify-write that spreads `...existing`. Route new writers through `buildNextCommunicationPreferences` rather than hand-rolling the document shape.
- **An absent preference is not consent.** `isLifecycleEmailAllowed` requires `lifecycleEmailsEnabled === true`; it used to return true unless the flag was explicitly `false`, which meant Ascend was sending on a permission nobody had given and could not evidence if beehiiv asked for it. The document is shared, so it exists for climbers who only ever changed a push preference - checking that it exists proves nothing. Never soften this back to `!== false`, and never add a second gate that treats undefined as allowed. The decision carries `lifecycleEmailsDecidedAt` (server time, stamped by `buildNextCommunicationPreferences` whenever the flag is written) and `lifecycleEmailsSource` (`onboarding` / `settings` from the app via the allowlist in `isAppLifecycleEmailConsentSource`, `email_link` from the unsubscribe endpoint). That trio is the consent record; a write that changes the flag without it is not, so `buildNextCommunicationPreferences` refuses a flag that arrives without a source rather than letting the new decision inherit the previous one's provenance.
- The lifecycle email preference is gated twice: once when the job is queued and again in `processEmailJobs` right before it sends. Both gates are required - a retrying job backs off up to ~14 hours, so a queue-time-only check would still deliver mail to someone who unsubscribed in that window. A job suppressed at send time gets the terminal `skipped` status, never `failed` - nothing went wrong and there is nothing to retry. The gate applies only to jobs carrying a `recipientUid`; admin feedback mail has no uid and always sends.

## Email copy
Email copy, templates, lifecycle automations, and subject lines must follow the Ascend Email Playbook. Codex has this as the `ascend-email-playbook` skill at `~/.codex/skills/ascend-email-playbook`; other agents should apply the same rule set: app-triggered emails go through Cloud Functions/Resend with deterministic dedupe, copy is competitive/stair-stepper-specific, and each email has one primary CTA.

## Cloud Functions emulator gotchas
- The Functions emulator proxies the `firebase-admin` namespace and strips its statics: inside it, `admin.firestore` is a function but `admin.firestore.Timestamp` and `.FieldValue` are `undefined`, so code using them throws only under the emulator and works in production. Import from the modular entry point instead (`import {Timestamp} from "firebase-admin/firestore"`) for anything that needs to run under `firebase emulators:start`.
- The Firestore emulator's REST API also enforces `firestore.rules`; seed fixtures with an `Authorization: Bearer owner` header to get the admin bypass.
